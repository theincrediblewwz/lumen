## 1. 工作方式（工程规范）

> 目标：用规范的软件工程方法，把一个"不那么快能做完"的项目稳定推进到可用。

### 1.1 迭代节奏

| 项 | 约定 |
| --- | --- |
| 迭代单位 | **里程碑（M0–M7）**，每个里程碑结束即产生一个可演示的增量 |
| 检查点 | 每个里程碑结束时：更新本文件状态表 + 写一条 `progress.log` + 跑全量测试 |
| 节奏建议 | 每周至少推进一个里程碑的若干任务；周内不追完美，周末做一次整理与回归 |
| 范围控制 | 新需求**不直接插队**，先记入 §6 待办池，下次排期时决定（防止需求蔓延） |

### 1.2 分支与提交

```
main         稳定可发布，只接受来自 develop 的合并
develop      集成分支，里程碑完成并验收后合入 main
feat/M#-名   功能分支，如 feat/M2-canvas-engine
fix/M#-名    缺陷修复
docs/…       文档
```

**提交信息**遵循 [Conventional Commits](https://www.conventionalcommits.org/)（中文正文即可）：

```
feat(canvas): 支持以光标为锚点缩放
fix(reader): 修复 $$ 块内 `=` 独占行被解析为 setext 标题
docs(design): 补充 AI 工具调用的 token 预算策略
test(engine): 迁移 mdread check_offline 回归套件
```

### 1.3 完成定义（DoD）

一个任务只有满足**全部**条件才算"完成"：

- [ ] 功能行为符合 DESIGN.md 中对应 FR 的**验收标准**，且手工验证过
- [ ] 相关单测 / E2E 通过；渲染内核改动必须过 `npm run check`
- [ ] 无 `tsc` / `lint` 错误，无 console 报错
- [ ] 性能不劣化（涉及画布或阅读器时，跑一次 §7 性能基线）
- [ ] 需要时同步更新 DESIGN.md 与本文档，并在 `progress.log` 追加一条记录
- [ ] 提交信息符合规范

### 1.4 进度追踪约定

- **`.dsh/todos.json`** —— 当前聚焦的任务清单（短期记忆，做完即划掉）
- **`.dsh/progress.log`** —— 按时间追加的进度日志（长期记忆，只追加不改写）

### 1.5 协作与构建节奏

> 原则：**提交要勤、构建要省、历史要干净。**

| 动作 | 频率 | 成本 | 说明 |
| --- | --- | --- | --- |
| **提交（commit）** | 勤快，按逻辑小步提交 | 几乎为零（本地秒级） | 小步提交便于回滚与定位问题，**不是浪费时间** |
| **推送（push）** | 每个工作段结束 | 几乎为零 | — |
| **CI 构建** | **仅在里程碑完成时打 tag 触发** | 高（macOS 10× 分钟） | 整轮预计 **4–6 次**（M2 / M4 / M5 / M7） |
| **日常验证** | 本地 `npm run dev` / `npm run check` | 零 CI 成本 | 开发期主要靠本地跑 |

**为什么不是"最后只构建一次"**：目标平台是 macOS、开发在 Windows 上进行，若到 M7 才第一次打包，签名、架构、路径、窗口安全区、WebView 差异会同时爆发。**按里程碑构建 = 把风险摊薄。**

**公开仓库策略**：开发期私有，功能成型后转公开。

- 公开后 GitHub Actions 标准 runner **分钟数不限**；
- 公开前整理历史：用 `git rebase -i` 压成若干有意义的提交，或新建仓库导入干净快照（既保住回滚能力，又不外泄探索过程）；
- 公开后红线：Actions 日志对外可见，**任何 secret 不得 echo**；仓库内不得有密钥。

**签名策略**：一期**不做代码签名与公证**，出 ad-hoc 构建（自用 + 极小范围分享够用，首次运行需右键 → 打开）。待公开发布时补 CI secrets 即可（见 DESIGN §11.4）。
